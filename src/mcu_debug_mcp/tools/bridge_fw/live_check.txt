【3】用 mcu-debug-mcp 的总线工具打真桥（port=COM21）
----------------------------------------------------------------
【3.1 bridge_probe】
桥自检（bus=-　桥：NUCLEO-H563ZI）
  端口       : COM21
  协议       : MCUDBG/1 ✓ 与工具一致
  桥支持     : i2c,spi,1w
  ⓘ 未声明支持：RS485 —— 用到这些的工具会收到 -ERR，不是接线问题。

  桥活着、认协议。下一步再怀疑接线和器件。
----------------------------------------------------------------
【3.2 i2c_scan】
桥拒绝了这条命令：-ERR TIMEOUT sda/scl stuck low (bus busy)
  ⓘ 总线超时。常见原因是 SDA 或 SCL 被某个器件**拉死在低电平**（总线卡死）—— 典型场景是主控在从设备发字节的中途复位。处置：断电重新上电，或在 SCL 上补 9 个时钟把从设备的状态机顶出来。
  （命令：I2C SCAN 0 8 119）
----------------------------------------------------------------
【3.3 spi_scan】
SPI 扫描（逐 CS 读 JEDEC ID 0x9F）（bus=0　桥：NUCLEO-H563ZI）
  ⓘ SPI **没有地址概念**，所以「扫描」只能是逐条 CS 发 0x9F：只有遵守
    0x9F 的 SPI NOR/NAND flash 会被列出来。SPI 传感器 / ADC / 显示驱动
    各有自己的命令字 —— 扫不到它们属于正常，不是故障（用 spi_read_reg 指命令）。

  CS0      0xFFFFFF  —— 无器件（全 1：MISO 被上拉/悬空，没人在驱动它）
  CS1      0xFFFFFF  —— 无器件（全 1：MISO 被上拉/悬空，没人在驱动它）

  结论：没有任何一条 CS 上读出有效 JEDEC ID。
  这**不代表 SPI 坏了** —— 三种常见情形：
    1) 板上挂的是 SPI 传感器/ADC（例如 ICM-426xx、ADS 系列），
       它们不认 0x9F，要用自己的命令字（spi_read_reg 指命令）；
    2) CS 脚号配错了（桥固件里的槽位表要对着你的接线改）；
    3) MISO 悬空（读回全 1）或没接。
----------------------------------------------------------------
【3.4 spi_read_reg(0x9F,3)】
SPI 读（bus=0　桥：NUCLEO-H563ZI）
  CS         : 0     命令字: 0x9F
  读到       : 0xff,0xff,0xff
  十进制     : 255 255 255

  ⓘ 全 0 / 全 1 通常意味着「这条件命令在从设备上不成立」或「MISO 没人驱动」，
    而不是「寄存器的值就是 0 / 0xFF」。先核对命令字，再查 MISO 接线。
----------------------------------------------------------------
【3.5 onewire_scan】
1-Wire 搜索 ROM（bus=0　桥：NUCLEO-H563ZI）
  没有找到任何 1-Wire 器件。
  ⓘ 常见原因：1) 数据线缺 4.7k 上拉（1-Wire 靠上拉给寄生电容充电，
    缺了必然搜不到）；2) 器件在寄生供电模式但总线没有强上拉；
    3) 线太长/容性太大（降速或加短接）；4) 桥固件里 1-Wire 用的引脚不对。
----------------------------------------------------------------
【3.6 rs485_send】
桥拒绝了这条命令：-ERR NOBUS rs485 transceiver not fitted on this bridge
  ⓘ 桥固件里没有配置这条总线（bus 编号对不上，或固件没打开该控制器）。
  （命令：RS485 SEND 0 2.0 48656c6c6f）
