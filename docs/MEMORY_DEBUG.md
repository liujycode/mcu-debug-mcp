# 内存问题诊断方法论（能力项 G11）

## 为什么单开一篇

「跑一会儿就死」「偶发 HardFault」「数据偶尔错一位」——这类问题八成是内存。

但内存问题有个**和其它 bug 都不同**的特点：**它不报错**。栈溢出、堆碎片、越界写，
多数时候一条日志都不产生，或者只在崩溃那一刻留下一个硬件故障地址。所以这里
必须靠方法，不能靠猜。本文写的就是「先做什么、看什么、怎么排除」。

## 一、先分类：三种完全不同的「内存问题」

| 类型 | 典型症状 | 关键指标 | 主要手段 |
|---|---|---|---|
| **栈溢出** | 局部变量多 / 有递归时崩；函数返回地址被破坏（回到不相干的地址） | 栈水位（high water mark） | 量栈用量，改栈配置 / 减局部变量 |
| **堆问题** | `malloc`/`free` 若干轮后偶发崩；长期运行后分配失败 | 堆峰值、剩余量、碎片 | 改静态分配 / 定长内存池，禁用动态分配 |
| **越界 / 野指针** | 随机崩、改到不相干的变量、现象不可复现 | MPU 违规地址、`BFAR`/`MMFAR` | MPU 划保护区 + 抓 HardFault 现场 |

**第一步永远是分类**。三类问题的排查路径完全不同，混着查会一直在原地打转。

## 二、栈：先量，再改（不要先猜大小）

1. **量水位**：多数 RTOS 提供 `uxTaskGetStackHighWaterMark`（FreeRTOS）或在启动时
   用固定魔数（`0xA5A5A5A5`）填满栈区，跑一遍最坏场景后回看被改写到哪。
   —— **没量过栈就调大栈，等于闭着眼改**。
2. **看中断上下文**：Cortex-M 进中断时用当前栈（MSP 或 PSP）。如果 RTOS 任务用
   PSP、中断用 MSP，那**中断里也在吃栈**——两部分都要留量。
3. **典型吃栈大户**：`printf`/`sprintf` 格式化缓冲、大结构体局部变量、浮点运算与
   `double` 的库调用、递归下降解析、以及「把整个帧缓冲搬到局部数组」。
4. **改法**：能改静态/全局的就别放栈上；确实要用大缓冲，改成 `static` 或从堆上
   一次性分配好（前提是堆本来就有）。

## 三、堆：动态分配在 MCU 上要慎用

1. **碎片**：小块反复申请释放，总剩余量够、但没有连续块——分配失败与「还剩多少」
   无关。所以「看剩余 heap 还很多」**不能**证明堆没问题。
2. **判据**：长跑压测 + 打印堆峰值（不是当前值）；`malloc` 返回 `NULL` 的次数；
   以及每次分配大小的分布。
3. **推荐做法**：嵌入式里优先**定长内存池 / 静态数组回收队列**代替 `malloc`；
   真要用 heap，至少做到「启动时一次性分配、运行期不再 free」。

## 四、越界与野指针：靠 MPU 与 HardFault 现场

1. **打开 MPU 保护区**：把数组边界之外、或关键数据结构所在的页设成
   no-access / read-only。越界写会**立刻**触发 MemManage fault，而不是几小时后
   在别处崩——把「不可复现」变成「可复现」。
2. **抓 HardFault 现场**：Cortex-M 的 CFSR/HFSR/BFAR/MMFAR 会告诉你：
   - 是总线错误、内存管理错误还是用法错误；
   - 出错时访问的地址（`BFAR`/`MMFAR`）——**这个地址直接指向越界的目标**。
   用本工具 `decode_fault(cfsr=..., hfsr=..., bfar=..., mmfar=...)` 直译位域。
3. **常见构造型越界**：`memcpy` 长度算错（尤其是「字节数 vs 元素个数」）、
   结构体 `#pragma pack` 与对齐不一致、DMA 长度与实际缓冲不匹配、
   环形缓冲「写指针追上读指针」。

## 五、本工具能帮的 / 帮不上的（别指望它做全部）

**能帮上**：

- `decode_fault` —— CFSR/HFSR/BFAR/MMFAR 位域直译，说清是哪类故障、地址是多少；
- `parse_map` —— 从 `.map` / `.elf` 看 RAM/Flash 实际占用，确认是不是真的装不下；
- `symbol_lookup` —— 把 PC/LR 地址换成函数名（ARM Thumb 下最低位是标志位，已处理）；
- `stack_unwind` —— 还原调用栈；
- `analyze_log` —— 日志里出现 `HardFault` / 栈溢出 / malloc 失败等模式时给出线索。

**帮不上（需要在固件侧或调试器里做）**：

- 栈水位 / 堆峰值 —— 要在固件里埋魔数或调 RTOS API；
- MPU 配置 —— 属于固件设计；
- 实时监控分配行为 —— 需要 hook `malloc`/`free`。

**如实说清这条边界**：工具负责「给你第一手证据和方向」，具体埋点还得在固件侧做。

## 六、直接可用的排查清单

- [ ] 先分类：栈 / 堆 / 越界，确定一条主线再动手
- [ ] 栈：量过水位了吗？中断栈算进去了吗？
- [ ] 堆：`malloc` 返回 `NULL` 统计过吗？有没有长跑压测？
- [ ] 越界：能不能用 MPU 把「偶发」变「必现」？
- [ ] 崩溃现场：CFSR/HFSR/BFAR/MMFAR 拿到了吗？（`decode_fault` 直译）
- [ ] 地址→函数：用 `.elf`/`.map` 把 PC/LR 落到具体函数（`symbol_lookup`）
- [ ] 固化：把这次的现场与结论写进回归用例，别让同一个坑踩第二次
